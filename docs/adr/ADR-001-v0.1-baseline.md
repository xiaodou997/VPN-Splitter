# ADR-001：v0.1 产品与架构基线

日期：2026-09-23  
状态：Accepted（产品与工程默认值）；技术可行性依赖 S0–S5 证据。  
决策依据：用户确认采用讨论中的推荐方案。  
替代：初始文档中关于平台架构、发行、语言、失败行为等未决项。  
总入口：[完整方案](../plan-v0.1.md)。

## 背景

项目有 WireGuard、OpenVPN 和第三方官方客户端三种来源，但真正需求是本机统一分流和恢复，而不是三个连接按钮。已有设计容易把 Split DNS 与精确域名分流、路由例外与双向任意分流、规则存在与保证执行混为一谈。

## 已接受决策

D01：macOS 26.0+，首发 arm64，GitHub Release/DMG，Developer ID 签名公证；不优先 App Store、Intel 或 Windows。

D02：自有代码 MIT；Swift/SwiftUI，纯 Swift PolicyCore；暂不增加 Rust。第三方许可证独立审查。

D03：多配置、单活动会话；主场景默认 DIRECT，指定目标 VPN。能等价替代官方客户端时优先 Managed；保留 External 作为受限兼容路径。

D04：Managed 基于 Packet Tunnel System Extension。WireGuardKit 为优先候选并分离协议 AllowedIPs 与系统路由；OpenVPN 3 Core 为优先研究对象，经许可和 NE 嵌入验证后使用。

D05：External v0.1 只承诺验证路由型全局 VPN 的 DIRECT 例外，不承诺 Include，不更改第三方 DNS，不注入/修改第三方程序，不绕过强制策略。Unknown 和 Conflict 必须可停止。

D06：统一规则先经能力检查再执行。first-match 要求编译后等价；REJECT/未支持 IPv6 规则拒绝激活，不静默跳过。

D07：域名分流接受 DNS-derived 限制；精确 DOMAIN 显式 opt-in；DOMAIN-SUFFIX 只支持 Managed 固定 CIDR 覆盖组合，预览其网段扩大效应。严格共享 IP 分离、任意公网后缀发现需另行设计。

D08：首发不是系统级防泄漏工具。不主动把 VPN 规则改成 DIRECT，但不保证断线不直连；IPv6 未覆盖显式提示，不全局禁用。要求 fail-closed/全地址族/严格域名的策略拒绝激活。

D09：先 S0 对真实场景做小验证，再 S1 WireGuard/签名、S2 DNS、S3 OpenVPN、S4 External 工程化、S5 发布验收。不能以两个 Managed 后端成功代替原场景价值验证。

D10：诊断、授权、凭据保护、可安全撤销和测试证据从首个实现开始；日志和路由指纹不是绝对所有权证明，歧义时不盲删。

## 后果与取舍

减少首发平台、并发与流量层能力可缩小工程面，但不消除签名、DNS 和第三方兼容风险。用户会看到明确的“不支持/未覆盖”，而不是虚假的全部生效。

DNS-derived 域名规则会影响同 IP 的其他流量，且不能保证应用独立解析的覆盖。External 受 OS、第三方客户端和实际网络状态约束，必须每个支持样本有证据。

不提供 Kill Switch 意味着隧道消失后可能存在直连；这是已接受的产品边界，不是待测试才决定是否告知的细节。

## 仍须通过后续 ADR 固定的实现细节

ADR-002：确切 target/entitlement/toolchain、WireGuardKit revision/适配点、enforceRoutes 实测选择。  
ADR-003：系统解析接口、有效期更新、DNS-derived 实际范围。  
ADR-004：OpenVPN revision、许可审查、桥接线程/包通道、认证选项矩阵。  
ADR-005：External 路由执行 API、支持条件、事务/租约/熔断参数。

这些不是未回答的产品问题，而是不能在真机验证前假装成立的技术细节。

## 拒绝的替代方案

不先 Fork 整个参考 App；不同时开工三套完整后端；不靠 route-nopull 一项参数代表 OpenVPN 架构；不把 Packet Tunnel 当默认 DNS 代理/内容过滤器；不让 Helper 暴露任意 root 命令；不以无限抢路由实现兼容。
